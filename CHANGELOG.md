# Changelog

## Unreleased
- **The sandbox can install Python dependencies.** The egress allowlist now includes PyPI (`pypi.org` and `files.pythonhosted.org`) next to the npm registry, so a project whose test command runs `pip install` can be verified. Before, `pip` got "403 Forbidden" from the proxy and the run failed verification through no fault of the agent. Existing configs list their allowlist explicitly (`sandbox.egress.allow`), so add the two hosts there and restart; new configs get them by default.
- **Pipelines failing after a merge now show up in the Inbox.** For GitHub projects the factory reads the workflow runs on the base branch; a workflow whose latest finished run failed is listed as *Failing after merge* with the run's link and the PR it came from, counted in the Inbox badge, and cleared by itself when a later run passes (cancelled and in-progress runs are ignored). Cached for two minutes; opt out per project with `deployWatch: false`. Replayed on Ossicone's real history it flagged both failed deploys of the redesign session.
- **PRs name the changed files the test command did not cover.** If the verify command runs in specific folders (`cd frontend && ...`, `--prefix web`, `-C api`) and the change also touches code elsewhere, the PR's Provenance section lists those files under *Not covered by that command*, and the run records `coverage`. It never blocks; it says nothing when the command runs from the repository root.
- **docs/gaps-and-roadmap.md:** the known gaps found in a real 17-ticket run, what is built, and the design of what is not (visual check stage, ticket file allowlist, overlap sequencing, why a ticket is waiting).
- **Settings page: choose the model, change the guardrails, no restart.** New `#/settings` view and `GET/POST /api/settings`: pick the agent's model and reasoning effort (from the models your Codex login offers; effort choices follow the model), and edit runs per day, attempts, time limit, parallel projects and daily budget. Everything is validated against ranges, saved to the config file and logged under *Recent changes*; it applies from the next run. **Check what a run will use** runs one tiny prompt in the same container and shows what Codex reports. Each run record now stores the agent, model and effort it was asked for (`agent` in `runs.jsonl`). Unpinned runs use whatever Codex defaults to, which was reasoning effort "none" on Codex 0.169. Settings are not an MCP operation, on purpose. The agent type, sandbox and projects stay file-only.
- **Fix: a stray "null" appeared at the top of every page** of the UI (the header passed `null` to `replaceChildren`).
- **Tests no longer leak temp folders.** `npm test` now runs through `scripts/run-tests.mjs`, which gives the run its own temporary folder and deletes it afterwards. Before, the suite left behind thousands of throwaway repositories and state folders in the OS temp directory (over 20,000 after a long session).
- **Fix: commits failed on a machine with no git identity.** The agent's work was done and verified, then `git commit` stopped with "Author identity unknown" (found by running the full loop on a clean machine). The commit now falls back to `Agent Factory <agent-factory@localhost>` for whichever of name/email is missing, and never overrides an identity you have (config or environment). Regression test reproduces a machine with no git config.
- **Fix: `init` said "Done" when the agent login had failed.** It now says setup is not complete, explains how to log in, and exits non-zero. Safe to re-run.
- **`npm run demo` / `agent-factory demo`:** a populated factory with no Docker, no accounts and no agent, built in about a second in a throwaway folder and deleted on exit. Two sample projects on the built-in tracker and local forge, with real git branches and PRs (one merge-ready, one blocked because its branch changed after verification), a launched plan with a dependency still waiting, tickets in every state, real code analysis, and sample history so the Flow card has data. Only agent runs are pre-recorded, and a banner says so. Found by a clean-machine install test, where nothing but `drill` could be tried without Docker.
- **Clearer first-run messages:** a missing config now says `npm run init` (or the `npx` route, or `npm run demo`) instead of `agent-factory init`, which isn't on a fresh clone's PATH. The README says plainly that the full loop needs Docker and a logged-in agent.
- **Real-model drill (`npm run drill:real`):** runs your configured agent on a scratch local-forge project with six adversarial tickets (failing test, "delete the test", edit CI, commit a credential, instructions planted in a repo file, an open-ended ticket) and records what it did and what stopped it. First results (Codex) in `docs/evidence/` and `docs/WORKFLOW.md` section 9a: no unsafe outcome in two runs; the model deleted a test when asked and the factory's check sent it back; the model did not ask a question on an open-ended ticket.
- **`requireVerify` policy:** with `limits.requireVerify` (or per project), a project with no test command gets no agent run; the ticket is parked with what to do. The Portfolio shows an *unverified* badge and a next step for such projects. New drill: `unverified-blocked` (9 drills now).
- **Flow metrics:** lifecycle events (ready, claimed, PR opened, parked, failed, closed) are recorded to `state/events.jsonl`, and `flow_metrics` (REST `/api/flow`, MCP, CLI) plus a Portfolio *Flow* card report ready-to-merged, queue/build/review/decision waits, first-pass and rework rates, machine-checked share, and attempts and cost per accepted change, with an explicit warning while the sample is under five accepted changes.
- **`agent-factory drill` / `npm run drill`:** a repeatable proof that the guardrails hold. It runs the real ticket loop, real git and the real local forge against a scripted agent that misbehaves on purpose (vague ticket, committed secret, CI edit, weakened test, killed run, replaced worker, review backlog, unsafe merge) and prints pass/fail with evidence per guardrail; exits non-zero if any fails. No network, Docker or accounts. Also runs in CI. Deliberately breaking three guardrails made exactly the matching drill fail.
- **docs/WORKFLOW.md:** the workflow written as a system: stages, where AI is and is not trusted, context and session boundaries, validation, guardrails mapped to drills, a log of real failure modes, production risks, and open risks.
- **Fix: runs were not verified in monorepos.** The test command analysis detects (for example `cd api && npm ci && npm test`) was shown in the Code tab but not used when a run executed, so projects whose tests live in a sub-folder ran unverified (and `doctor` counted them as verified). A run now uses, in order: the repo's `.agent-factory.json`, the project's own setting, the analysis-detected command, then a look at the repository root. Found while adopting library parts in three real projects.
- **Fix: Python detection.** `pytest` is installed alongside `requirements.txt` (many requirements files omit it), and a Python project with no tests now has no detected command instead of one that always fails ("no tests ran").
- **Set a test command on an existing project:** the "no way to run tests was found" warning told you to set one but there was nowhere to do it. The Code tab now has a *How the agent's work is checked* card (test command and container image), backed by `POST /api/projects/<id>/verify`. The repository's own `.agent-factory.json` still wins; empty clears it and detection applies again.
- **Chunk-level repeated-code detection** (replaces whole-file matching as the main signal): functions, classes and methods, React components and hooks, and Express routes are fingerprinted separately (JS/TS and Python), tagged by what they do (api-client, auth, database, retry, cache, streaming, validation, llm, adapter, hook, component), grouped across projects and **ranked by value**. Classes that share an interface but not code are reported as a *same interface* pattern. Fingerprints are stored per project in `state/projects/<id>/chunks.json`, not the config. Template files (Dockerfile, tsconfig, installers) are low value and are only collected on request (`templates: true`).
- **Local forge** (`host.kind: "local"`): a bare git repository and pull-request records per project, no account or token. Review the diff, comment, merge (fast-forward or clean merge commit; conflicts refused; blocked if the branch changed since verification or touches protected files) and close in the UI, REST or CLI. Merge and publish are human-only.
- **Publish:** set a publish target (GitHub, GitLab, Bitbucket, any git remote) and push the base branch (never forced; refuses a diverged remote), optionally switching the project to the real repository. Also a `publish` scenario step that must follow an approval.
- `create_project` / the new-project form can create a local project (`host: "local"`) and take a test command (`verify`). CLI: `add --host=local [--import=…]`, `merge`, `publish`.
- Repository hardening found by test: the local repo ignores hooks in its own config; clones use `file://`; objects are fsck-checked.
- README brought up to date (local-first mode, tracker and host tables, an honest verified / not-verified list).
- **Built-in tracker** (`local` ticket source): issues, epics, comments and states inside the factory, no account needed; plans, scenarios, webhooks and the factory loop work on it unchanged. New project **Tracker** tab (epics with progress, ticket page with comments, close/reopen/requeue); board cards open the ticket. New API: ticket detail and tracker overview; `reopen` ticket action.
- **Tests cannot be quietly weakened:** removed assertions, deleted test files and switched-off tests in a run are flagged by the quality gate (retry once, then flag; `blockTestWeakening` to block). New tests are never penalised.
- **Fencing:** claims carry a token that is re-checked before anything is pushed or written to the tracker; a run that was replaced or expired pushes nothing and cannot release the replacement's lease.
- **Review backlog cap:** `limits.maxOpenReviews` stops claiming new tickets while that many agent PRs wait for review.
- **Provenance:** PRs and work orders name the brief revision and the verified commit (or say nothing machine-checked it).
- Ideas and gaps in this round came from a review of Mark McDonald's draft "Agentic-First Engineering Playbook".
- **Studio** replaces the Control room's intake box (which moved to the Studio as "Add work to a project"): start a project from a brief with a **target** (prototype or deploy) and an optional house style; the Control room now opens with a launcher and a live "building now" strip. "Cells" left the header (the Portfolio covers it).
- **Targets and readiness:** `set_target`, `project_readiness`; the Portfolio shows "Ready to deploy: n of m checks" with the checklist. A human still approves any go-live.
- **Plans in the tracker:** launching a plan creates **epics in Ossicone (verified live) and Jira (tested against a fake)** with tickets linked to them. Epics show tracker links on the Plan tab. The agent on a plan ticket is told **where it fits** (plan, done, in flight, what depends on it).
- **House styles:** part kinds theme, pattern, form and skill; profiles (parts + conventions) saved in the library (`profiles/<slug>.json`), applied per project (`profile_list|save|set`, Library → House styles). Every ticket in such a project gets the conventions, skills and parts.
- **Parallel lanes:** `limits.parallelProjects` (1 to 8) builds projects at the same time; `/api/status` reports lanes; Health warns when the disk is nearly full.
- **Extension platform:** **plugins** (hash-pinned, human-enabled, offline: add scenario steps, operations, quality rules, part kinds, ticket sources and code hosts), **scenarios** (JSON workflows with checks, ticket steps, restricted HTTPS calls and human approval gates; dry run by default; persisted runs; secrets declared and redacted; `allowHosts`), and **overridable prompts** (`prompts/task-rules.md`). Bundled `prototype` and `ship` scenarios, a `cloudflare` plugin (DNS upsert and Pages deployment; dry runs show the exact change) and a `deploy-hook` plugin. Scenarios page (runs, approvals, extensions) and `agent-factory plugin|scenario` commands. Approving a gate and enabling a plugin are not available to agents or MCP.
- **Self-modification guardrails:** the repository's `.agent-factory.json` protects the security core (git safety, sandbox, egress, server auth, plugin loader, scenario engine, CI, licence) from the factory's own edits.
- docs/EXTENDING.md: how to change how it works and which services it uses, what is and isn't pluggable yet, and the security model.
- **Try it:** run an exported function of a library part in a sandbox (QuickJS: no network or files, 3 s) from the part page or `agent-factory library try`.
- **Extract cleanly:** a ticket that asks the agent to move tangled code into a standalone module with its own tests, ready to promote (`library extract`, button on repeated-code cards).
- **Alerts become tickets:** a private webhook per project (`/hook/<project>/<secret>`) that turns alerts from trackers, monitors or scripts into tickets: checked, de-duplicated by key, rate-limited, secret rotatable. Card on the Brief tab; `webhook_info` / `webhook_rotate` operations.
- Fixes: the add-source panel showed `[object HTMLInputElement]`; part pages could print "null" for missing sections.
- **Portfolio page** (every project from brief to shipped, next step for each, "Needs you" list) and a planning prompt on the Control room, so briefs, plans and the library are discoverable.
- **Stale-tab fix:** the UI tells an already-open browser tab when the factory was updated and offers a reload (build id in `/api/status`).
- **Library page** in the UI: set up or connect the library, searchable part cards with API, usage, file viewer, tests and who uses which version; **Repeated code** with a promote form; **Upgrades**; and a how-it-works tab. `library_*` MCP operations, `agent-factory library …` CLI, header navigation tightened for the extra item.
- **Reuse library (backend, CLI and MCP):** a git repo you own holds tested parts (`parts/<slug>/part.json`, `src/`, `test/`, README). Create or connect it (`agent-factory library create|connect`), find repeated code across projects (`library candidates`; renamed copies are found too), promote it as a PR (`library promote`), search it (`library search`), and queue a ticket to use a part (`library use`). Before every run the factory tells the agent which parts match the ticket and provides their files; afterwards it records reuse in `.factory/parts.lock.json` and on the PR. New files that rewrite a part are flagged by the quality gate (one retry, then a flag). Version bumps open upgrade tickets in projects on the old version.
- **Project Pack** (Brief and Plan tabs): a structured brief (goal, users, scope, out of scope, done criteria, constraints), conventions, decisions and source material (files, links, text) for every project; the agent drafts a delivery **plan** (epics, small tickets with acceptance criteria and dependencies) you edit and launch; tickets are released as their dependencies are merged. Every agent run receives the relevant context. Publish the pack to the repo as a PR under `.factory/`.
- **Agent-native control:** `agent-factory portfolio | brief | source | plan | ops | op | agents-md` drive a running factory from the terminal (or any AI agent); `create_project`/`add_project` accept a brief and a plan request; new MCP operations for briefs, sources, plans, analysis and a portfolio view. See docs/AGENT-GUIDE.md.
- The create-new-project form is now brief-first (the one-box description is a quick start).
- **Code explorer redesign:** the Code tab now has Overview, Findings, Files, Repeated code, Tests and Ignored sub-tabs. Findings show the real code line (secrets masked), why it matters and how to fix it, deep links to the line on the code host, search, severity/kind filters, grouping, and per-finding Queue fix / Ignore file. Files view with sizes, test status and findings per file. The CLI honours `.gitignore` in your own working copy.
- **Ignore files in the analysis and the PR gate:** lock files, minified/generated files, snapshots, build output and images are skipped by default; add your own patterns per project (Code tab), globally or in the repo's `.agent-factory.json`. The Code tab shows what was skipped.
- **Security fix:** git commands on the host no longer run repository-controlled code (hooks, fsmonitor, sshCommand, credential helpers, `ext::` or redirected remotes planted by the agent in `.git`). See SECURITY.md.
- **Built-in code inspection** (no server, no download): a Code tab per project with folder layout, repeated code (exact files and lines), untested files, and our own quality rules with a trend; each finding can be queued as a ticket. `agent-factory analyze <folder|url>` prints the same report in the terminal.
- **Quality gate on the agent's own change**: only the lines it added or changed are checked (one retry; a leftover secret stops the PR, other findings are flagged on it). Tested with a real agent.
- Re-analysis is a background job with live progress. (An optional SonarQube integration was built and then removed again: it needed a 1.4 GB download and 10% free disk.)
- **Repository analysis** on add (and Re-analyze): language, package manager, detected test command (including apps in subfolders), A–E ratings for size, tests, duplication, upkeep and committed secrets, with an editable verify command. Saved with the project, summarised in the agent prompt, and flagged on Health when a project has no way to verify.
- The ticket pre-check now only blocks tickets too short to act on; the agent proceeds on stated assumptions or asks specific questions (`NEEDS_INFO:`).
- Pasting any repository URL (web, `.git`, ssh) is accepted.

## 0.3.0
- **Control room UI** redesigned: live assembly line with a monoline animated icon per station, work-order pages, ticker, light and dark themes, self-hosted fonts.
- **Inbox**: act on everything that needs a human (add detail and requeue, comment, edit, close, review PRs). Also available over MCP.
- **Pluggable trackers and code hosts**: GitHub Issues, Ossicone, Jira, Linear; GitHub, GitLab, Bitbucket, any git remote. Guided setup with connection tests.
- **MCP server** with Code Mode (`/mcp-code`, about 270 tokens) and direct tools (`/mcp`).
- `/healthz` for uptime monitors; `service` command prints a systemd unit; agent logins run inside Docker.
- Fixes: tickets created from the UI are found immediately (GitHub's lists lag by seconds); closed tickets no longer count as queued; Ossicone ticket links and numeric comment ids; animation jitter from full-page redraws.
