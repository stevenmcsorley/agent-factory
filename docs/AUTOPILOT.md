# Autopilot: schedules, roles, skills, designs and autonomous mode

Everything here is off or neutral by default. With nothing switched on, the factory behaves exactly as before: one agent builds each ticket, opens a draft PR, and a human merges.
All of it can be driven from the UI (a project's **Autopilot** and **Designs** tabs, the **Skills** page, **Settings**) and from MCP (`search` for the tool names below).

## Why is this waiting?
`why_waiting` (and the Autopilot tab's "Right now" card) lists every reason a ready ticket is not being picked up: the factory is paused, the project is paused, it is outside its schedule, the daily run cap or budget is reached. Each reason says when it can resume.

## Notifications (`set_notifications`, `test_notification`)
One address (https, or http on this machine) gets a small JSON POST when something needs you: `pr-ready`, `merged`, `failed`, `parked` (needs detail or a decision), `deploy-failing`, `cap-reached`, `held`. An ntfy.sh topic works as-is and shows on your phone; the `text` field suits Slack-style webhooks. Duplicates within a minute are dropped, at most 30 go out a minute, and a down destination never affects the factory. The address is the only secret, so make it hard to guess. Ready tickets also show on the board why they are waiting.

## Schedules (`set_schedule`)
Per project: `startAt` (nothing before this date), `hoursPerDay` (agent time per local day, counted from recorded runs), `windows` (`[{days:[0-6], from:"22:00", to:"06:00"}]`, may cross midnight; after midnight a window belongs to the day it started on), `priority` (1 first to 9 last when many projects are due), `stopWhenDone` (pause the project when its plan is complete). Times are the machine's local time. A run already in progress is never cut off at a boundary; the next one simply does not start.
For 100 projects at 5 hours a day each: give them all `hoursPerDay: 5`, give the important ones a lower `priority`, and keep `limits.parallelProjects` and `maxRunsPerDay` at what your plan can carry.

## Roles (`get_roles`, `set_roles`, `set_project_roles`)
`builder` (always on), `reviewer` (optional), `tester` (optional: when the builder changes source code but adds no tests, a second agent writes them. It may only add or change test files, the whole test command must pass again, and if either rule is broken everything it did is undone and the builder's change is exactly as it was), `security` (optional second reviewer that looks only for security problems; runs with the reviewer or on its own, and any blocking finding from either sends the change back), `designer`, `fixer` (CI failures and review comments on an open PR), `planner`, `spec-writer` (optional: when a ticket is too vague to start, drafts acceptance criteria, scope and assumptions into it, once, clearly marked as agent-drafted, instead of parking it), `skill-writer`. Each can use its own model and reasoning effort. The reviewer is a second agent run that reads the change before its PR opens, on a throwaway copy of the workspace so it cannot alter what it is judging. Blocking findings go back to the builder; if they are still unresolved on the last attempt the PR opens **flagged** on its Provenance note. An unreadable verdict counts as an error, never an approval. It costs one extra agent run per attempt, so it is off until you turn it on (globally or per project).

## Skills (`list_skills`, `save_skill`, `preview_skills`, `draft_skill`, ...)
A skill is a Markdown file with a small header (name, description, roles, projects) that agents receive for a kind of work. Fourteen built-ins ship, each crediting what inspired it in its `source` line (written in our own words; the sources are MIT-licensed or used for ideas only): test-driven-development, bugfix (root cause first), verification-before-completion, test-writing, receiving-code-review, ci-failure-triage, code-review (spec and standards as separate axes), security-review, ui-design, accessibility, writing-plans, ticket-slicing, spec-writing and skill-writing. Each goes only to the roles it suits, so the builder is not given the reviewer's checklist. saving a skill with a built-in's name makes your own copy, and deleting it restores the built-in. `preview_skills` shows exactly what a role would get on a project. The skill-writer drafts or improves a skill from a description; the draft is only ever shown to you to read, edit and save.

## Designs (`create_design`, `revise_design`, `edit_design`, `approve_design`, ...)
Ask the designer for a mockup. It reads the brief and your approved designs and writes one self-contained HTML file. You review it (desktop and phone width), ask for changes (the next version keeps what you did not mention), edit the HTML yourself, and approve or reject. **Only approved designs reach the builder**, with their stylesheet and the full file under `.factory-context/designs/`. Mockups are cleaned on the way in (no scripts, frames or outside requests) and previewed in a sandboxed frame from a short-lived unguessable address under a policy that allows no scripts and no network.

### Keeping designs organised
The Designs tab is a library, not a pile. At the top, **What the builder follows** lists every design currently in use (and, under "Exactly what the builder is told", the literal text that goes into each ticket). Below it, designs are grouped as **In use**, **Waiting for you** and **Archived and rejected**, with search and a Screens / Artwork filter. Each design shows one line saying what the builder does with it.
- **Versions.** Every design keeps its versions in a table: v3 *latest* *not reviewed*, v2, v1 *in use*. **Use this one** puts any version in use; **View** previews it; **Delete** removes a version for good (never the one in use, nor the last one). A newer version of a design that is in use waits for you: the builder keeps using the approved version until you choose another.
- **Areas.** Give a design an *area* ("Login screen", "Brand"). Only one approved design per area guides the builder: approving a new one archives the old one automatically (it keeps its history and points at what replaced it).
- **Archive or delete.** *Archive* keeps everything and stops the builder following it; *Restore* brings it back as waiting for your approval, never silently in use. *Delete for good* removes it and all its versions.
- **Limit.** The builder is told about the 6 most recently updated designs in use; if more are approved the panel warns you and says which are over.
MCP: `designs_in_use`, `archive_design`, `restore_design`, `update_design` (title, area), `delete_design_version`, plus `area` on `create_design`.

### Artwork (logos, icons, illustrations)
A design can be a **set of SVG artwork** instead of a screen (`create_design` with `kind: "assets"`, or "Artwork" on the request form). The designer draws up to 12 files as code, you see them on a contact sheet (light and dark, at 96, 40 and 20 px), ask for changes, edit any file by hand, and approve. Approved artwork tells the builder to use those files rather than draw its own. **`publish_assets`** (or "Open a pull request" under an approved set) clones the project, writes the files into a folder you choose (`assets/brand`, `public/images`, `src/assets`...) and opens a pull request for you to review and merge. It works the same for a new project and an existing one, on any host the factory can open PRs on. SVGs are cleaned on the way in (no scripts, no outside references, no embedded images). It draws vector art only: there is no photo or painted-image generation, which would need an image-model service added as an integration.

### Screenshots of the current app (`capture_screenshots`, `get_screenshots`)
For a project with the visual check set up, **Capture now** (Designs tab) starts the app from its base branch in the browser container and takes light and dark screenshots of every route at phone, tablet and desktop width, plus a summary of each page's real title, headings, buttons, fonts and colours. The designer is handed the light phone and desktop shots and the summary, so a redesign or new screen starts from what exists. Capturing never changes the visual-check baseline. Limits: it needs the visual-check preview (start command, port, routes) and the app has to run in the sandbox without its real backend; a live URL elsewhere cannot be captured (attach a screenshot as source material instead). Whether the model can look at the PNGs depends on the agent, which is why the text summary is included too.

## Autonomous mode (`set_autonomy_allowed`, `set_autonomy`, `autonomy_status`)
**This merges pull requests without a human.** It is opt-in twice: a factory-wide switch (Settings) and a per-project mode. Turning the factory-wide switch off stops every project at once.
A PR merges only when all of these hold: the run ended ok; the quality gate passed; a test command checked the change and covers the files it touched; the reviewer agent approved (unless you turn that requirement off); CI is green and finished; no review comment is unhandled; and today's per-project and factory-wide merge caps are not reached. Anything else is *held*, with the reasons shown on the Autopilot tab. Every merge is written to `state/audit.jsonl`, commented on the ticket, and the ticket is closed.
After merging, a pipeline that breaks becomes **one fix ticket per failing run**, at most `fixAttemptsPerWorkflow` per workflow (the count resets when it is green again), then it stops and leaves it to you.
Supported for GitHub (`gh pr ready` + squash merge; branch protection that needs a human approval makes `gh` refuse, and that is reported as a held reason, never forced), GitLab (drops the Draft prefix, squash-merges, deletes the branch), Bitbucket (the same with `[Draft]`) and the local forge. Verified against real GitHub on a scratch repo; GitLab and Bitbucket are only tested against fakes so far, so try them on a scratch repo first.

## Ticket file allowlist
A ticket can include a fenced block listing the only files that may change:

    ```allowed-files
    src/billing/**
    test/billing.test.js
    ```

A change touching anything else is refused: the agent gets one chance to put the extra files back, and if it does not, nothing is pushed.

A ticket that declares `allowed-files` also **waits while an open pull request changes any of those files**, so two changes to the same files do not collide. It goes as soon as that PR is merged or closed; the reason is shown on the project's Autopilot tab. Tickets without the block are never held.

## Visual check (`set_preview`, `visual_check_now`, `get_preview`)
Tests and typechecks cannot see a layout that breaks on a phone, text you cannot read, or a page that throws. With a project's **preview** set (how to start the app, its port, the routes to load), the factory, after a change passes its tests, starts the app in the sandbox and loads every route at 360, 768 and 1280 px (light and dark) in a real Chromium. It looks for: sideways scroll, text below WCAG contrast (under 3:1 fails, under 4.5:1 is a warning), tap targets under 44 px on the phone width (warning), console errors and uncaught exceptions, pages that fail to load or answer 4xx/5xx. It only observes: it never clicks or types.
**Only new problems count.** Run "Check now" once on the base branch to record a baseline; later changes are judged on what they add, so an app with old problems is not blocked by them. New failures go back to the builder like a failing test (one retry per attempt); on the last attempt the PR opens with the problems listed on its Provenance note. A check that could not run (the app would not start, no browser image) is recorded and never blocks the PR. In autonomous mode, new failures and a check that could not run both hold the merge. Screenshots are kept with the run and shown on its page.
Setup: build the browser image once (`docker build -f Dockerfile.visual -t agent-factory-visual:latest .`, about 2.3 GB), then set the preview on the project's Autopilot tab or with `set_preview`. Images: the default `agent-factory-visual` (Node 22) covers Node dev servers and static sites; `Dockerfile.visual-python` adds Python, pip and venv for Django, Flask and FastAPI (set the project's preview `image`, and put the pip steps in `install`; verified with a real Flask app). Any other stack needs an image with Node 22 and Playwright at `/opt/pw`. Limits: pages that need a backend need that backend to be reachable or mocked by the dev server. The measurements are heuristics (for example, text over a gradient or image is not contrast-checked).

### Where the built-in skills come from
Chosen from the most-used public skill sets: obra/superpowers (MIT; systematic debugging, test-driven development, verification before completion, receiving code review, writing plans), mattpocock/skills (MIT; diagnosing bugs, two-axis code review, tickets as vertical slices), Anthropic's skills repository (frontend design, skill creator) and Trail of Bits' security skills (CC-BY-SA, so used for ideas only, nothing copied). They are re-written for how this factory works: one ticket, one workspace, one pull request.

## What the reviewers catch
Checked on a real model with a deliberately flawed change (SQL built by string concatenation, `add` changed to subtract, the existing test replaced by an empty one, no test for the new function): both the reviewer and the security reviewer returned "changes", the security pass flagged the injection as a blocker, and the reviewer also caught the broken `add`, the deleted test and the missing test. That is one example, not a measured detection rate.

## Live preview: use a project's site without deploying it
One gateway (default port `ui.previewPort`, which is `ui.port + 1`; `0` switches it off) serves every project on a **stable address**: `http://<project>.localhost:7778/` for the main branch, and `http://<project>--<branch>.localhost:7778/` for a branch or pull request ("Preview this branch" on a local-forge PR). `http://localhost:7778/` lists every project. Opening a project's address starts its preview on its own; it then follows the branch (re-fetching within a few seconds of a merge) and is dropped after two idle hours. Static sites only: the files are served as they are and nothing is built or run. Dotfiles, symlinks and repository history are never served.
Why `*.localhost` on its own port: browsers send those names to this machine, and each project is a separate origin, so a site's JavaScript can read neither another project's storage nor the factory UI's (which is on a different port and holds your sign-in token). Only this machine can reach it. MCP: `start_live_preview`, `list_live_previews`, `stop_live_preview`.

## The agent bench (Control room)
Under the conveyor on the Control room's line there is one tile per agent role, in pipeline order: Spec writer, Builder, Test command, Tester, Visual check, Reviewer, Security reviewer, then Designer, Planner and Fixer. A tile lights up while that agent works and shows what it is doing ("writing the change · attempt 1"), on which project and ticket (a link to the run), how long it has been at it, and which model and effort it uses. Idle tiles are dimmed; optional roles appear only when some project uses them. It also shows the work that is not a run at all: the designer drawing artwork, the planner reading a brief, the skill writer, and the visual check. The test command and visual check are drawn with dashed borders because the factory runs them, not an agent. The same data is on `GET /api/activity` (`agents` and `roster`).

## The plan's usage limit, and auto-resume
Your agent plan has a usage limit that resets at a set time. When ANY agent (the builder, a reviewer, the designer, the planner...) reports it, the factory records the limit and **pauses every agent** until the time the CLI names, instead of starting the next ticket only to fail it. The Control room shows a banner, `why_waiting` says "the agent plan's usage limit is reached; agents resume ... ", new designs, plans and skill drafts are refused with the same message, and a notification (`limit-reached`, then `plan-resumed`) is sent if you have them on. The limit survives a restart (it is saved, and re-derived from the last rate-limited run).
- **Auto-resume (on by default).** A ticket stopped by the limit stays queued (it is not marked failed). When the time passes the factory starts again by itself, and any ticket the limit had already failed is put back in the queue; tickets that failed for a real reason are left for you. Switch it off in Settings (or `set_settings({ autoResume: false })`) to stay paused until you press **Resume anyway** (or `resume_after_limit`).
- **Reading the time.** "10:26 PM" means the next time that comes round; a full date ("Nov 22nd, 2026 3:28 AM") is taken as written; if no time can be read the pause is 30 minutes and then it tries again. Two minutes of margin are added.
- `agent_plan_status` reports it over MCP. Settings (model, effort, limits, auto-resume) are all MCP-controllable now (`get_settings`, `set_settings`); the agent type, sandbox, network allowlist, UI host and project list stay in the config file.

## Where the agent plan goes (usage measurement)
Every agent call, whichever role makes it (builder, reviewer, security, tester, spec-writer, designer, planner, fixer, skill-writer), is logged to `state/usage.jsonl` with its project, run and ticket, and its tokens split into **fresh input**, **cached input** and **output**. The Orders page shows the split by role, by project and by day, the costliest runs and the average text sent per call; each run's page shows what that run used by role; `usage_report` (MCP) and `GET /api/usage` return the same.
Why the split: an agent re-sends its whole conversation at every step, so "input tokens" is mostly text the provider has cached and bills at a small fraction (Codex's published rate card prices cached input at about a tenth of fresh input and output at several times it; its limits run in rolling five-hour windows plus weekly caps). The **estimate** shown is in fresh-input equivalents (fresh ×1, cached ×0.1, output ×6). Those weights are approximations kept in one place (`src/usage.mjs`), not measured quota: correct them if the rate card differs. `input_tokens` is treated as including the cached part; a source that reports more cached than input is treated as counting them separately. Runs from before the log existed only have the builder's total and no cached split, so they are counted as all fresh (an over-estimate, flagged on the page).

## Setups (presets): the same agent set-up everywhere, and by default for new projects
A **setup** is a named bundle: the factory's default model and effort (`agent`), a model and effort per role (`roles`), and which optional agents (reviewer, security, tester, spec-writer) are switched on for a project (`projectRoles`). Built-in setups name no model, so they work on any login: **lean** (builder plus reviewer), **standard** (recommended: reviewer, security, tester and spec writer on, low effort) and **thorough** (standard, with medium effort for the designer and planner). You can save your own from what you have now, or build one over MCP that names models. Autonomous merging is never part of a setup; it stays an explicit per-project choice.
- **Apply** sets the default model/effort and each role's model/effort (replacing earlier per-role choices); with `projects: "all"` (or a list) it also switches the optional agents on or off for those existing projects, and nothing else in them changes. An unknown project id refuses the whole apply.
- **New projects** start with the default setup's optional agents (`makeDefault` / `set_new_project_setup`). Existing projects are never changed by that.
- UI: Settings, "Agent setup". MCP: `list_setups`, `save_setup`, `apply_setup`, `delete_setup`, `set_new_project_setup`. REST: `/api/setups`.
- What the evidence supports: the built-ins vary effort and which agents are on, not models, because in a test the reviewer on the strongest model caught a repo-specific CI rule that cheaper models missed. Put a cheaper model on a role only after measuring it on the Orders page.

## What the agents are given, and what is optimised
Each ticket's prompt is about 2 to 7 thousand tokens (the task rules, the project brief and conventions, the stylesheets of the approved designs, the skills for the role, then the ticket). The files the agent can open are separate and can be much larger (on one project, three design mockups of 31 to 52 KB). Most of a run's "input" is the agent's own conversation re-sent at every step, which the provider caches.
- **Ordering for the cache (done).** The prompt now puts everything that is the same for every ticket first (rules, brief, conventions, approved designs, skills) and what depends on this ticket last (the source excerpts that match it, its plan entry, reusable parts, then the ticket). A provider can reuse its cache of an identical beginning, so consecutive tickets in one project share a longer cached start. Nothing is removed.
- **Steps are counted.** Each call records how many steps (commands, edits, searches) the agent took, so the Orders page can show average steps per call and input per step: it separates "many steps" from "a large context".
- **Not changed yet:** which design files an agent is told to read, which skills are sent, and whether helpers run on small changes. Each is a quality decision to make from the measurements.

## Reviewing what the factory built (Inbox)
On a **local forge** project a pull request in the Inbox can be handled where you see it: **Review the changes** opens its page (diff, comments, a live preview of the branch), **Merge** accepts it and **closes its ticket**, **Reject** closes the pull request without merging and marks its ticket **failed**. Above the buttons is what the reviewers found (their verdict, the blocking findings with file and line, the visual check, the tests the tester added) and, if autonomous mode is holding it, why.
- **Merge is the only way a change becomes "done".** A ticket whose pull request is still open cannot be closed as done (the Inbox button and the API refuse with a clear message). If a ticket is closed some other way while its pull request is open, the plan treats it as *in review*, not done, so nothing that depends on it starts. Otherwise the next ticket would build on a main branch that does not contain the work it depends on, and recreate it.
- **Reject does not move the plan on.** Whatever depends on a rejected ticket keeps waiting until you requeue and merge it.
- For GitHub, GitLab and Bitbucket the review link goes to the host and merging happens there.

### Conflicts, merge order, rebuilding, and stuck plans
- **Unmerged work is always visible.** The Inbox lists every open pull request, including ones whose ticket was closed (they are flagged "the ticket was closed, but this change was never merged"). A plan that has nothing running and is waiting on pull requests or failures gets its own card ("Plans waiting on you") naming exactly why, and one notification (`plan-stuck`) per situation.
- **Would it merge?** For a local forge each pull request shows, computed from the repository, whether it would conflict with the main branch right now (and in which files), how far main has moved on, and which other open pull requests touch the same files. "Sort out #2 first" follows the plan's order. A conflicting PR cannot be merged; the button is disabled.
- **Rebuild on current main** closes the attempt and sends the ticket back to the factory, told which files conflicted ("main already contains them; do not recreate shared files") and what the reviewers found. **Reject and try again** does the same with your reason. Plain **Reject** closes it and marks the ticket failed. Over MCP: `pr_check`, `reject_pr`, `rebuild_pr`. Merging is deliberately not an agent operation.
- **Every host.** "Closed" is never taken to mean "merged": the plan asks the host (GitHub, GitLab, Bitbucket and the local forge all answer) what became of the pull request. A ticket closed after its PR was closed without merging is *failed*; one whose PR is open is *in review*; only a merged one is done (and remembered, so the host is not asked again).

## Unattended mode, fix rounds and automatic conflict resolution
Autonomous mode used to stop at the first pull request the reviewers disliked. It now tries to **fix** what it holds, a bounded number of times, before it waits for you.
- **Fix rounds** (`fixReviewRounds`, default 2, 0 turns it off): a pull request held because the reviewers asked for changes gets a round: the builder is given their findings and addresses them, the project's tests run, the reviewers look again, and the result is pushed. The merge gate is then re-evaluated; if the reviewers now approve (and everything else passes) it merges. When the rounds are used up it stays held, the "plan is waiting" card appears and you are notified. A verdict with only minor notes already counts as approval, so only serious findings trigger a round.
- **Automatic conflict resolution** (`autoResolveConflicts`, default on, local forge): before the fix round a conflicting PR gets the same resolver as the **Resolve conflicts** button, then a fresh review.
- A round never merges, never commits as the agent, refuses protected paths, and is recorded (audit trail, Orders) like any other run.
- **Unattended mode** is the one switch for all of it: `set_unattended` (MCP), the **Unattended mode** card on the project's Autopilot tab, or `POST /api/projects/:id/unattended`. It turns on the reviewer, tester and spec writer (the security reviewer is a choice; off suits a static site), autonomous merging, fix rounds and conflict resolution together. It needs a test command and the factory-wide switch, and says what is missing rather than half-applying. `unattended_status` reports it; `on:false` stops autonomous merging.
- Limits to know: merges per day (default 20 for this mode; the factory-wide limit in Settings still applies), and fix rounds are per pull request.

### Designs and artwork first
Unattended mode starts with a **design pass**: the designer makes one screen per page named in the brief (the `*.html` files in the scope, up to 5) and one artwork set from the artwork sources, each approved automatically, and the tickets are not released until they exist, so every builder follows them. Pages that already have a design are skipped. Switch it off with `designs:false`, run it by hand with **Make designs now** or `design_project` (`approve:false` leaves them for you to review). Progress is in `unattended_status` (`design`).

## The design stage (design first, then build)
Like a studio, a project with a UI starts with its designs. **Design is stage zero of the plan**: when a plan is launched for a project whose brief or plan names HTML pages (mode `auto`; `on` and `off` are explicit, `set_design_phase` / the Design stage card), the designer makes one screen per page (up to 5) and one artwork set, and **no build ticket is released until they are approved**. You approve them in the Designs tab (or **Approve all designs** / `approve_designs`); an unattended project approves them itself. If the designer stops (for example the usage limit) the stage shows *failed* and tickets wait: retry (`retry_design_phase`) or skip the designs for this plan (`skip_design_phase`).
- **Every ticket is told which screen it builds.** A ticket whose "Creates:" or "Builds:" line names a page gets that page's approved mockup path and the artwork, with an instruction to match it (the written copy wins on wording). Tickets are stamped with the design version they were built from.
- **Reviewers get an objective check**: the built page's headings and navigation compared with the approved design, in the review context, plus an instruction to compare the change with the screen. (Words only: looks stay the reviewers' judgement.)
- **Drift**: an approved design newer than what a page was built from is listed (`design_phase_status`, the Design stage card).
- **Restyle or rebrand an existing project** (`restyle_project`, the Restyle card): describe the new direction; the designer looks at what exists (screenshots when the visual check is set up), designs the key pages (or all) and, when the direction mentions a brand, logo or illustrations, new artwork. Approve them, then **`match_designs`** plans the tickets: the shared look first, then the artwork, then one per page, each told to keep content, behaviour and tests. `approve:true, match:true` (or unattended) does all of it automatically. It needs no plan to be running.

## Token economy: what each agent is sent
Measured on a real project (Orders page, and `usage_report`): an ordinary small ticket is one builder call plus one reviewer call (about 4% of a project each); the cost is dominated by (1) tickets that need several review rounds, (2) context re-sent at every step of an agent run (about 90% of it cached, so cheap), and (3) the designs pass.
- **Builders**: a ticket that is told which screen it builds gets a *slim* design context: every screen listed with its mockup path, but only one shared stylesheet (not one per screen) and no designer's chatter. Tickets that build no page get the full context.
- **Reviewers** are sent what they need (the brief, this ticket's screen and source excerpts, its place in the plan, the automatic design check), not the builder's skills, reusable parts or every stylesheet.
- On the project measured this cut the builder's context from about 12,000 to 8,000 tokens and the reviewer's from about 12,000 to 4,400 per step.
- The biggest remaining lever is ticket size: a ticket that restyles a whole site needed four builds and seven reviews. Split broad tickets by page or component.

## Measuring how a change should be reviewed (reviewer benchmark)
`node scripts/review-bench.mjs [--strategies=shot,shot_rules,atoms,agent] [--cases=...] [--save]` runs 8 planted defects and 3 clean changes through different reviewer strategies with the real agent and reports, per strategy, what it caught (and for the right reason), what clean change it wrongly blocked, and the tokens used (measured like production). Strategies: `agent` (today's reviewer: a full agent exploring a checkout), `shot` (one call, diff only, an empty directory), `shot_rules` (the same plus the repository's written rules), `atoms` (four narrow specialists, one call each). It runs in a throwaway state folder; `--save` writes the result to `docs/evidence/`. Use it before changing how reviews work, or which model reviews.

## The OpenRouter agent (free models, swapped as they run out)
An agent provider built on OpenRouter, with its own page (Models). The agent loop is the factory's own (read, search, edit, run-in-sandbox tools; the API key never enters a container), so the model can be **swapped in the middle of a task** when it runs out: the conversation is plain messages any tool-capable model can continue.
- **Router.** For each step it picks the best *ready* free model with tool calling: a prior from size, name and context, then what has actually happened (success rate, bad tool calls, speed). A model that hits a limit **rests**: the rest starts from how long that model really took to come back last time (learned, shown on the page), doubles if it fails again, and a daily-allowance limit waits for the reset. Paid models are never used unless `allowPaid` is on.
- **Use.** `set_openrouter` / the page: `enabled`; `roles` that use free models first (`["*"]` for all); `fallback` to carry on when the Codex plan is limited or unavailable (nothing pauses, and a call that hits the plan limit mid-run is redone on a free model); `banned` and `pinned` models. The key is the secret `OPENROUTER_API_KEY` in `state/secrets.env` (UI or file; no MCP tool takes it).
- **Page** (Models): key status, ready/resting counts, what is running now and on which model, what each agent would use, every model's state, return time, success, speed and tokens, recent calls, Test / Ban / Wake.
- **Limits worth knowing.** Free tiers allow about 20 requests a minute and a daily allowance (50 requests a day on a free key; more once the account has a little credit). Free models vary in tool-calling quality; use `scripts/review-bench.mjs` before trusting one with a role. Some free providers may log prompts: keep private code on `fallback` only until that is decided.

**The free allowance, measured.** A free OpenRouter key allows **50 free-model requests a day** (resets at midnight UTC); adding $10 of credit raises it to **1,000**. A tool-using task spends 5 to 40 requests, so the agent refuses to start one it cannot finish; **reviews are one request** (diff only, no tools); tool calls are batched per reply. The page shows requests left today. An autonomous pass also re-runs a review that could not run (a limit or timeout) instead of holding the PR.

## Who does the work: Codex, free models, or both (delegation)
`cfg.agents = { mode, routes }`, the **Agents and models** page, `agent_policy` / `set_agent_policy`. **Mode**: `mix` (default), `codex` (Codex only: when the plan is limited, work waits) or `openrouter` (free models only). **Routes** per role: `codex`, `openrouter` or `auto`; yours beats the default, and the page shows each default and why.
- **Mix defaults.** Reviewer: free models, as **one request** (the diff, the ticket, the brief and the repository's own written rules are in the prompt; no tools, no exploring); if the answer is not a parseable verdict the review is redone on Codex. Spec writer, skill writer, tester, designer: `auto` (free models first, Codex if they cannot answer). Builder and fixer: `auto` = a **small (size S) ticket on its first attempt** goes to the free models; a bigger ticket, an unknown size or **any retry goes to Codex**. Planner and security reviewer: Codex (the planner for quality; the security verdict is not benchmarked on free models yet).
- **When Codex is limited** the free models carry on automatically (nothing pauses), except for a role you set to Codex. When the free models are limited or the day's allowance is used, Codex does the job. Each provider's limit is tracked separately; only Codex's is the "plan limit".
- **Evidence** (`docs/evidence/review-bench-*.json`, `scripts/review-bench.mjs --provider=openrouter`): on 8 planted defects and 3 clean changes, a free model reviewing from the diff alone caught 7 of 8, with the repo's written rules in the prompt 7 of 8 (a different one missed), four narrow specialist calls 8 of 8, and a tool-using free-model agent 7 of 8; none blocked a clean change. A one-request review is about 1,200 tokens against about 90,000 for the Codex reviewer. The sample is small and each case ran once: treat differences of one case as noise, and re-run the benchmark after changing a model or prompt.
- The page also shows where the tokens went (Codex vs free models, by role, last 7 days) and how often a free model could not answer and Codex did.

## Local models (a third provider)
Local models run on your own hardware through Ollama, LM Studio, llama.cpp or vLLM (anything with the OpenAI chat API; Ollama is used through its own API so the context size can be set). They are **off until you switch them on** (Agents → Local models, or MCP `set_local { enabled: true }`), and even then nothing goes to them by itself:
- **Local only** (mode `local`): everything runs locally. Nothing is sent to anyone; if no local model is ready, work waits.
- **A role routed to Local** (`set_agent_policy { routes: { reviewer: "local" } }`): local first; if the answer cannot be used (a review that does not parse, an empty reply, a server that is down) the free models do the job, then Codex.
- **Stand-in**: when Codex is limited and the free models are not available, local models carry on, except for a role you pinned to Codex or in codex-only mode.
Which models are eligible: they must fit the memory limit (default about 55% of the machine's memory; `maxGb`), judging jobs (reviews) can use any model, and building jobs need tool calling. Models Ollama lists as `:cloud` run on Ollama's servers: they are flagged and kept out unless `allowRemote` is set. A failing model rests (the server being down 1 minute, out of memory 10, missing 30) and returns by itself; speed and reliability are learned per model. Local requests need no key, have no allowance and cost nothing; their cost is time, so on a CPU only small models and short jobs make sense. Measure before routing: `node scripts/review-bench.mjs --provider=local --model=qwen2.5:3b` runs the reviewer corpus on that model and reports how many real defects it caught.

Measured on a 4-core, 12 GB laptop with no graphics card (reviewer benchmark, 11 cases, 8 planted defects, one request each, 2026-11-22): `qwen2.5:3b` caught 3 of 8 with no false blocks (about 90 s a review); `granite4:micro-h` caught 1 of 8; the Codex reviewer caught 7 to 8 of 8. So small local models are not good enough to be the reviewer: use them as a last-resort stand-in, or on a stronger machine. A model needs its file size plus room for the context window (an 8B model at 16k context needs about 6.3 GB), which is why `llama3.1:8b` is skipped here unless `maxGb` or the context size is changed.
